# Queue rules version 4: the simulation's fixes, then steps 5-8 (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** finish the queue design (version 4), so the simple rules hold in every case:
- the simulation's 15 rule breaks (S1-S15) and A2 are fixed (step 4c);
- Save's memory survives Android closing the app's screen;
- then Vibe batches with "On the way" (step 5), stations and Shuffle the Jukebox as chained lists (step 6), the button back up to the playing song (step 7), and Vibe (step 8).

**Spec:** `docs/superpowers/specs/2026-11-05-queue-rules-design.md` (version 4: rules 1-8, section 4 stations, 5a Vibe, Order steps 4c-8). Ideal model: `docs/superpowers/specs/2026-11-06-queue-architecture.md`.

**Evidence:**
- simulation findings, each with a minimal spec case: `/tmp/claude-0/-home-user-CyberJuke/bd98eba3-056a-5b13-9650-b0b6bbadf4aa/scratchpad/sim-report/findings.md`;
- the cases in spec format: `.../sim-report/findings-cases.json`;
- the code map for steps 5-8: `.../scratchpad/steps58-map.md`.

**Tech Stack:** Preact + signals (web), Kotlin + Media3 (native), Vitest, pure-JVM JUnit, Playwright.

## Global Constraints

- **Web and native change together.**
  - Every queue rule is a case in `tests/spec/queue-rules.json`, run by `src/player/queueRules.test.ts` and `QueueRulesTest.kt`.
  - Each case is shown failing first on the runner(s) it fails on.
  - Kotlin is checked here with the pure-JVM harness (`scratchpad/ql/run-ops.sh`, `run-ls.sh`, `fuzz-both.sh`, pointed at the worktree in use) and in CI. PlaybackService, StateEncoder, JukePlayerPlugin and ExoQueueHost compile in CI only: match existing patterns exactly.
- **Gates:** `npm run check` passes on every commit with 0 lint warnings. Logs never carry track ids. Never "YouTube Music" in UI text (it's "Global").
- **Commits:** subject `Area: what changed`, with a body explaining why, plus the session trailers. Each visible change gets a CHANGELOG `[Unreleased]` line in the plain user tone, and a TESTING.md phone check where only a phone can show it.
- **UI decisions are delegated by the maintainer (6 Nov):**
  - follow the house style (labels like `// NOW PLAYING`, `link-btn`, `icon-btn`, existing tokens);
  - no new colours;
  - screenshots of the result go in the PR body.
- **One PR per phase** (A-E), each merged when CI is green on all 8 checks, before the next phase starts.
- **Review:** each task gets a task review. Each phase ends with a whole-branch review and one fix wave.

## Review Focus

1. Both queues stay equal step for step: re-run the simulation's parity and invariant explorers (`sim-report/explore.ts`, `parity.ts`, `run-findings.sh`) at the end of phase A and of phase B. All of `findings-cases.json` must pass on both runners.
2. Queued songs under every new operation: re-run the queued-songs fuzz (`ql/fuzz-both.sh`).
3. Screen locked: whatever the player needs next must already be on the phone (rule 2). The web side can be asleep.

- [ ] **Shuffle on:** everything before the current list's marker stays behind, as Played does. Only the current list's unheard songs are mixed. Songs you walked back over stay ahead, unmixed.

### Task 2: The loop (S5, S4)

**Files:** `queue.ts` (`next` wrap, `settle`, `setRepeat`); `QueueOrder.kt` (`onTransition`, loop handling); `PlaybackService.kt` only if a seek is needed; spec + runners.

- [ ] Spec first: the S5 and S4 cases, plus A5's wording (Repeat all drops unheard songs of earlier lists, pinned).
- [ ] **S5, web:** the loop goes to the first song in play order that isn't a heard queued one.
- [ ] **S5, native:** Media3 wraps to window 0 by itself. In `onTransition(forward)` on a loop, if the new current is a heard queued song, drop it with the rest and seek to the first song that stays. That one loop isn't gapless, and only in this case.
- [ ] **S4:** with Repeat all on, a song from before `listStart` (one you walked back to) leaves once another song plays. Web: in `settle`; native: in `onTransition`. Never the current song, never a queued one.
- [ ] Commit `Player: the loop never starts at a queued song you heard, and an earlier list's song leaves it`.
